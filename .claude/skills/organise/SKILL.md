# Organise the folder

Make the layout deterministic. Every other job in this kit finds files by convention, so when a file is in the wrong place, or named the wrong way, the job does not fail loudly, it quietly works from less than it should have. This job fixes that and then says what it did.

It is a bounded job by construction. It creates approved folders, moves approved files, and reports. It never deletes or overwrites. Every change, even one move, requires the user's approval of a written plan.

## Input

$ARGUMENTS:

- empty: survey everything, propose the changes, make them, report
- `check`: survey and report only, change nothing, not even a folder
- a file or folder name: fix that one thing and report on it

## The layout this kit expects

```
company/
  profile.md                  your facts, gitignored
  profile.template.md         blank, tracked
  profile.example.md          fictional example, tracked
  .env.local                  SAM.gov Public API Key, gitignored
  .env.local.example          no key in it, tracked
pipeline/
  opportunity.template.md     tracked
  README.md                   tracked
  <solicitation-number>.md    one per tracked opportunity, gitignored
proposals/
  README.md                   tracked
  <solicitation-number>/      one folder per opportunity, gitignored
    compliance-matrix.md
    volume-1-technical.md
    volume-2-management.md
    volume-3-past-performance.md
    reps-and-certs-todo.md
    gaps.md
    submission-checklist.md
    package/
data/
  README.md                   tracked
  sam.db                      local copy of the SAM.gov notices, gitignored
tools/
  samdb.py                    the database tool, tracked, never edited by this job
  organise.py                 fixed-path move helper, tracked, never edited by this job
dashboard.html                generated by /dashboard, gitignored
```

`company/`, `pipeline/`, `proposals/`, and `data/` are created if they are missing, along with the README and template files if those are gone, taken from what is already in the repo. Nothing else is created. `data/sam.db` is never created by this job, never moved, and never opened; `/sync` and `/backfill` own it. If it is missing, say so in one line and offer `/backfill`.

## The naming convention

`pipeline/<solicitation-number>.md` and `proposals/<solicitation-number>/`, with the same number in both.

Take the solicitation or notice number exactly as the notice states it, then replace each character a filename cannot hold with a single dash. Those characters are `\ / : * ? " < > |`. Strip a trailing dot or space, which Windows will not keep either. Leave the case as the notice states it, do not pad it, do not shorten it, and do not add a date, an agency, or a title to the name. The number is the key that ties the pipeline file to the proposals folder, and both jobs on either side of this one look it up by that exact string.

When a pipeline file has no solicitation number in it at all, do not invent one. Leave the file where it is, list it under what was left alone, and say that the file needs its Solicitation or notice number row filled in before it can be named properly.

## Step 1, survey

List what is actually there with the assistant's file-listing and Read tools, scoped to the kit root and `company/`, `pipeline/`, and `proposals/`. Do not survey with a shell command. Read enough of each loose file to know what it is, not the whole thing.

For each file in `pipeline/` other than the template and the README, read the Solicitation or notice number row. That value, run through the naming convention, is what the file should be called.

For each folder in `proposals/`, note its name and whether a pipeline file matches it.

Never touch anything under `.claude/`, `.github/`, `docs/`, or `.git/`. Never move `README.md`, `CLAUDE.md`, `AGENTS.md`, `SECURITY.md`, `LICENSE`, `ONE-PROMPT.md`, `.gitignore`, `pipeline/opportunity.template.md`, `pipeline/README.md`, `proposals/README.md`, `company/profile.template.md`, `company/profile.example.md`, or `company/.env.local.example`. Those are the kit itself.

## Step 2, work out the plan

Build a list of changes. Each one is a create or a move, and each one names the file and where it goes.

Things that belong in the plan:

- a folder in the layout above that does not exist, created
- a pipeline file whose name does not match its own solicitation number, renamed
- a proposals folder whose name does not match the pipeline file's solicitation number, renamed to match the pipeline file, because the pipeline file holds the notice and is the authority
- an opportunity file sitting at the folder root, or in `proposals/`, or anywhere other than `pipeline/`, moved into `pipeline/` under the right name
- a draft, a matrix, or a volume sitting at the folder root or loose in `proposals/` rather than in `proposals/<solicitation-number>/`, moved into the right folder, matched by the solicitation number inside the file
- a profile written somewhere other than `company/profile.md`, moved

Things that never go in the plan:

- deleting anything, for any reason, including an empty folder or a file that looks like a duplicate
- overwriting a file that has content
- copying a file rather than moving it
- editing the contents of a file, other than a file this job created itself
- renaming anything in the tracked kit list above

Where the destination already exists and has content, that is a collision, not a change. Leave both files exactly where they are, and put the pair on the report under what needs a decision, with the two paths and their sizes so the user can look at them.

## Step 3, show the plan first

Print every plan and stop for explicit approval before touching anything. Print it as a list, one line per change, in the form `move pipeline/va-helpdesk.md to pipeline/47QTCA-25-R-0012.md`. Say how many files are affected. Then wait.

If the plan is empty, say the layout is already right and go straight to the drift report.

If `$ARGUMENTS` is `check`, print the plan and stop regardless of size.

## Step 4, make the changes

After approval, use the Write tool, never a shell command, to write the exact approved plan to `organise-plan.json` in this shape:

```json
{
  "directories": ["proposals/47QTCA-25-R-0012"],
  "moves": [
    {
      "source": "pipeline/va-helpdesk.md",
      "destination": "pipeline/47QTCA-25-R-0012.md"
    }
  ]
}
```

Then ask approval for one fixed command. State that it reads `organise-plan.json`, resolves every path inside this kit, rejects protected paths, path escapes, symlinks, missing sources, collisions, and destinations outside `company/`, `pipeline/`, or `proposals/`, then performs only the approved directory creates and moves. It never deletes, overwrites, or uses the network.

```text
Mac or Linux: python3 tools/organise.py
Windows: py -3 tools/organise.py
Windows fallback: python tools/organise.py
```

Run only the exact command the user approves. Do not add paths, solicitation numbers, variables, pipes, redirection, or other arguments. Never interpolate a value from a solicitation, notice, profile, or attachment into a shell command. If the helper refuses a move, stop and report its message. Do not work around the refusal with another command.

After the moves, if any file's contents refer to a path that has just changed, fix the reference in that file and say so. Do not change anything else inside a file.

## Step 5, the drift report

Drift is when the folders are laid out correctly and the work still does not line up. Report each of these that applies, in one line each, with the file path:

- An opportunity in `pipeline/` with no `proposals/` folder. Normal before a go decision. Worth a line when the pipeline file records a go decision, because that means drafting has not started.
- A `proposals/` folder with no pipeline file. This is the one that matters. The deadline, the submission method, and the set-aside all live in the pipeline file, so a draft with no pipeline file is being written against nothing. Say that plainly.
- A `proposals/` folder with volumes in it but no `compliance-matrix.md`. The volumes are being written against nothing to comply with. Offer `/compliance-matrix`.
- `company/profile.md` missing. Offer `/setup-profile`.
- `company/profile.md` present but still the example. Compare it against `company/profile.example.md`; if the identity block still names the fictional company or the example UEI, say that every downstream job is working from a fictional company. Offer `/setup-profile`.
- `company/.env.local` missing while there is evidence the API path is in use: `pipeline/.search-results.json` exists, or a pipeline file cites the SAM.gov API as its source. Point at the steps in the find-opps job. Do not open `company/.env.local` to check its contents, and do not print anything out of it.
- A pipeline file that was not built from `pipeline/opportunity.template.md`, so it has no notice table. The other jobs read that table by its row labels. Say which rows are missing.
- A pipeline file with an empty Response due date row. Say it plainly, near the top of the report. A tracked opportunity with no deadline is the failure mode this kit exists to prevent.
- `dashboard.html` present and older than the newest file in `pipeline/` or `proposals/`. Say the board is behind the files and offer `/dashboard`.

Report drift, do not fix it. Every item above needs a decision or a fact that only the user has.

## Step 6, the report

Four lists, in this order, each one line per item, each with a path:

1. Changed. What was created, and what moved from where to where.
2. Needs a decision. Collisions, and anything the plan could not resolve without a fact.
3. Drift. From step 5.
4. Left alone. Anything unrecognised that was not touched, with one clause on what it looks like. Never suggest deleting a file here. Say what it is and let the user decide.

Then one line: the single next thing worth doing, named as a command.

If nothing changed and nothing drifted, say that in one line and stop. Do not pad the report.

## Rules

- Never delete a file, a folder, or a line inside a file. Not an empty folder, not a duplicate, not something that looks like junk. This job has no delete in it at all, and if the user asks for one, say that this job does not delete and let them do it themselves.
- Never overwrite a file that has content. A collision is reported, not resolved.
- Move, never copy. Two copies of a proposal drifting apart is worse than one in the wrong place.
- Never make any change without showing the full plan and getting explicit approval.
- Never rename a file based on a solicitation number you inferred, remembered, or read off a similar file. It comes from the Solicitation or notice number row of that file, or the file is left alone.
- Never edit the contents of an opportunity file or a draft, beyond fixing a path this job has just changed.
- Never read or print `company/.env.local`.
- Never touch anything under `.claude/`, `.github/`, `docs/`, or `.git/`, and never move the kit's own tracked files.
- Never treat `company/profile.example.md` as the user's company, and never copy it over `company/profile.md`.
- Never put a path or a solicitation-derived value into a shell command. The only execution command is the fixed no-argument `tools/organise.py` command after approval.
